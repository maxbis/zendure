# Installation Manual

This document describes how to install and configure the Zendure project, including the cookie-based authentication used by `/login`.

## 1. How the Suite Is Divided

In practice, this project is split into three parts:

1. **Automation controller (`automate/`)**
   - This is the Python runtime that runs on a local device that can execute Python, for example a Raspberry Pi or another always-on Linux box.
   - It reads the battery state, reads a configured power meter, fetches the resolved schedule from the web app, and sends charge/discharge commands to the Zendure battery.

2. **Web app and schedule management (`main/`, `login/`)**
   - This is the PHP web interface where schedules, rules, prices, status, and automation information are shown and managed.
   - It also exposes the resolved schedule API that the automation controller consumes.

3. **Optional tools and emulation (`tools/`, `emulation/`)**
   - These scripts are for testing, inspection, API probing, and local emulation.
   - They are useful during setup and troubleshooting, but they are not required for a normal end-user installation.

This manual starts with the first part: the automation controller in [`automate/`]([install_dir]/automate).

## 2. Automation Controller (`automate/`)

### 2.1 What it is

The automation controller is the part that actually drives the battery.

The active runtime is:

- [`automate/automate_www.py`]([install_dir]/automate/automate_www.py)

This script runs continuously on a Python-capable device and acts as the bridge between:

- the **schedule** generated by the web app
- the **live power meter input** (P1 hardware or Shelly)
- the **live Zendure battery status**
- the **Zendure local device API** used to apply charge/discharge settings

It also exposes its own local monitoring API on port `1611`, which the web app can read for current battery, meter, and automation state.

### 2.2 High-level overview of how it works

At a high level, the automation loop works like this:

1. Load configuration from [`automate/config/config.jsonc`]([install_dir]/automate/config/config.jsonc).
2. Read the configured power meter.
3. Read the current Zendure device status.
4. Fetch or reuse the resolved schedule from the schedule API.
5. Determine what the battery should do right now.
6. Apply battery safety limits such as minimum and maximum state of charge.
7. Send a command to the Zendure device only when a change is needed.
8. Store status changes locally in SQLite and expose them through the built-in HTTP API.

The schedule is therefore not executed inside the PHP web app. The web app decides the plan, but the Python automation process performs the actual control.

### 2.3 Main inputs of the automation controller

The controller combines multiple inputs:

1. **Resolved schedule API**
   - Config key: `apiUrl`
   - Typical value:
     - `http://localhost/zendure/main/data/api/data_api.php?type=schedule&resolved=1`
   - This is the main automation input. It tells the Python controller which power mode or power value should apply at the current time.

2. **Power meter input**
   - Config key: `powerMeter`
   - Supported types in this repository:
     - `p1_hw`
     - `shelly`
   - This input is especially important for dynamic modes such as `netzero` and `netzero+`, where the controller adjusts power based on current grid import/export.

3. **Battery / Zendure status**
   - Config keys:
     - `deviceIp`
     - `deviceSn`
   - The controller reads the Zendure device to get live values such as battery charge level and current power settings.
   - These values are used to prevent charging above `MAX_CHARGE_LEVEL` or discharging below `MIN_CHARGE_LEVEL`.

4. **Local controller state**
   - The runtime also uses its own recent history, such as previous power setpoint, zero-count standby logic, and stored status updates in SQLite.
   - This is used for smoothing, standby transitions, and status reporting.

### 2.4 What a config is

The automation controller is driven by one config file:

- [`automate/config/config.jsonc`]([install_dir]/automate/config/config.jsonc)

This is a JSON-based configuration file with comment support. The loader accepts:

- full-line `//` comments
- `/* ... */` block comments

The config tells the automation process:

- whether it should run in test mode
- how to reach the Zendure battery
- which power meter implementation to use
- where to fetch the resolved schedule
- battery charge protection limits
- loop timing and standby behavior
- power thresholds and ramp limits
- where local runtime data should be stored

In other words, the config is the installation-specific wiring for the controller. The Python code stays the same; the config adapts it to a specific house, battery, meter, and schedule endpoint.

### 2.5 High-level capabilities

Based on the current code, the automation controller can:

- run continuously as a local control service
- fetch the active schedule from the web app
- apply fixed charge power values
- apply fixed discharge power values
- stop charging/discharging by setting power to `0`
- run **net-zero** mode
  - discharge only to reduce grid import toward zero
- run **net-zero+** mode
  - charge only to reduce grid export toward zero
- enforce minimum and maximum battery percentage limits
- limit sudden step changes in requested power
- use standby logic after repeated zero-power cycles
- expose a local API for status, P1 data, Zendure data, refresh requests, and Wh-per-hour calculations
- store local runtime history in SQLite for status and energy summaries

## 3. Web Application (`main/`)

### 3.1 What it is

The `main/` application is the browser-based control and monitoring interface.

Its main entry point is:

- [`main/charge_schedule_mobile.php`]([install_dir]/main/charge_schedule_mobile.php)

This application does not directly control the battery hardware itself. Instead, it:

- shows the current battery and grid status
- shows schedule and price information
- lets the user edit the schedule
- lets the user maintain conditional automation rules
- reads status back from the Python automation controller

In short:

- `automate/` is the runtime controller
- `main/` is the operator interface and schedule source

### 3.2 High-level overview of the functions

Based on the current code and documentation, the `main/` application provides these high-level functions:

- **Current battery status**
  - charging, discharging, or standby
  - battery percentage and estimated usable capacity
  - current charge/discharge power

- **System and grid details**
  - current P1/grid power
  - WiFi signal
  - system temperature
  - battery-pack details

- **Price overview**
  - today and tomorrow price bars
  - current, minimum, maximum, and average price information

- **Energy graph**
  - Wh charged and discharged per hour
  - based on data reported by the automation runtime

- **Schedule viewing**
  - resolved schedule for today
  - stored schedule entries with exact and wildcard patterns
  - visual overview bars for today and tomorrow

- **Schedule editing**
  - add a new schedule slot
  - edit existing schedule entries
  - delete entries
  - auto-calculate schedule proposals
  - clear outdated entries

- **Automation status**
  - see recent automation start, stop, refresh, and power-change events

- **Condition editor**
  - define rules that automatically influence the resolved schedule based on price and other conditions

### 3.3 Installation dependencies for `main/`

The web application depends on:

- PHP `8.x`
- a web server such as Apache or Nginx with PHP support
- read/write access for the PHP process to:
  - [`main/data/charge_schedule.json`]([install_dir]/main/data/charge_schedule.json)
  - [`main/data/charge_schedule_conditions.json`]([install_dir]/main/data/charge_schedule_conditions.json)
  - any cached data files used by the data API
- access from the web server to the automation runtime API, typically:
  - `http://YOUR_CONTROL_DEVICE:1611`

If the web app cannot reach the automation runtime, the schedule editor can still work, but status panels such as charge state, automation status, and energy graph will not show live data.

### 3.4 Main application data flow

At a high level, the `main/` app works like this:

1. The page loads in PHP and renders an initial dashboard.
2. JavaScript refreshes data from configured APIs.
3. Schedule data is read from the schedule JSON and resolved through the data API.
4. Price data is loaded from the price API.
5. Battery and automation data are loaded from the automation runtime through proxy endpoints.
6. User edits are written back to the JSON schedule files through PHP API endpoints.

This means the web app is both:

- a **dashboard**
- a **configuration source** for the automation controller

### 3.9 What the schedule editor does

The schedule editor in `charge_schedule_mobile.php` lets the user manage schedule entries that are stored in:

- [`main/data/charge_schedule.json`]([install_dir]/main/data/charge_schedule.json)

Each entry uses a 12-character key:

- `YYYYMMDDHHmm`

Wildcards `*` are allowed, so a single entry can describe a repeating pattern.

Examples:

- exact slot:
  - `202601151200`
- recurring daily time:
  - `********0800`
- date-specific wildcard time pattern:
  - `20260116****`

Supported schedule values are:

- a positive number for charging
- a negative number for discharging
- `0` for stop/standby
- `netzero`
- `netzero+`

### 3.10 What the condition editor does

The condition editor is:

- [`main/edit_rules.php`]([install_dir]/main/edit_rules.php)

It manages the rules stored in:

- [`main/data/charge_schedule_conditions.json`]([install_dir]/main/data/charge_schedule_conditions.json)

The condition editor is used to define conditional schedule behavior based on price and derived metrics.

Examples of what a rule can do:

- charge when price is below zero
- discharge only during the most expensive hours
- enable `netzero` or `netzero+` only in selected months or hours
- activate charge/discharge behavior only when the daily price spread is large enough

### 3.11 How the condition editor works

Each rule contains:

- `name`
- `value`
- optional filters such as `month`, `hour`, `min_time`, `max_time`
- a list of `conditions`

Rules are evaluated top to bottom.

Important behavior:

- first matching rule wins
- conditions are ANDed within a rule
- manual exact schedule entries keep higher priority than condition-generated values

Supported condition fields include:

- `price`
- `ranking`
- `min_price`
- `max_price`
- `spread_price`
- `min_price_hour`
- `max_price_hour`
- `month`
- `hour`
- `sunrise_hour`
- `sunset_hour`
- `electricity_level`

Supported outputs:

- integer power values
- `netzero`
- `netzero+`

The file is written atomically, so save operations replace the target file safely.

## 9. Automation Runtime API

The Python automation runtime in [`automate/automate_www.py`]([install_dir]/automate/automate_www.py) exposes an HTTP API on port `1611`.

Typical base URL:

- `http://YOUR_CONTROL_DEVICE:1611`

This API has two roles:

1. **Status/monitoring**
2. **Runtime control commands**

### 9.1 Monitoring endpoints

These endpoints are mainly consumed by the web app:

- `GET /api/test`
  - API health and endpoint inventory
- `GET /api/p1`
  - latest power-meter reading
- `GET /api/zendure`
  - latest Zendure reading
- `GET /api/status`
  - last status change
- `GET /api/all`
  - combined P1, Zendure, and last status
- `GET /api/automation_status`
  - recent automation events
- `GET /api/wh_per_hour`
  - charged/discharged Wh per hour
  - optional query param: `days`
  - example: `/api/wh_per_hour?days=7`
  - default is `3`, maximum is `30`
- `GET /api/status_updates_delta?after_id=...`
  - incremental status rows from SQLite

For `/api/p1` and `/api/zendure`, optional query parameters are supported:

- `max_age`
- `maxAge`

Value:

- `0` = always refresh
- positive integer = refresh only if cached data is older than that many seconds

### 9.2 Runtime control endpoints

These endpoints can actively control the automation runtime:

- `GET /api/refresh`
  - force a schedule refresh from the schedule API

- `POST /api/restart`
  - request a graceful automation-process restart

- `GET /api/pause`
  - read current pause state

- `POST /api/pause?state=on`
  - enable pause override
  - this forces desired power to `0`

- `POST /api/pause?state=off`
  - disable pause override
  - schedule-based control resumes

- `GET /api/loglevel`
  - read the current runtime log level

- `POST /api/loglevel?level=DEBUG`
- `POST /api/loglevel?level=INFO`
- `POST /api/loglevel?level=WARNING`
- `POST /api/loglevel?level=ERROR`
  - set the runtime log level immediately

The log-level endpoint accepts these parameter names:

- `level`
- `loglevel`
- `log_level`

### 9.3 Practical API examples

Examples:

```bash
curl http://YOUR_CONTROL_DEVICE:1611/api/test
curl http://YOUR_CONTROL_DEVICE:1611/api/all
curl http://YOUR_CONTROL_DEVICE:1611/api/refresh
curl -X POST "http://YOUR_CONTROL_DEVICE:1611/api/pause?state=on"
curl -X POST "http://YOUR_CONTROL_DEVICE:1611/api/pause?state=off"
curl http://YOUR_CONTROL_DEVICE:1611/api/loglevel
curl -X POST "http://YOUR_CONTROL_DEVICE:1611/api/loglevel?level=DEBUG"
curl -X POST "http://YOUR_CONTROL_DEVICE:1611/api/restart"
```

### 9.4 Installation note for API access

To make the web app work correctly, ensure the controller device allows HTTP access to port `1611` from the web server or browser environment that needs it.

If this port is blocked, the `main/` dashboard can still load, but live status and automation-control functions will fail.

## 10. Authentication (Cookie + Hash)

Authentication is validated by:

- `[install_dir]/login/validate.php`

Login page:

- `[install_dir]/login/index.php`

Allowed key storage:

- `[install_dir]/login/validkeys.txt`

### How it works

1. User enters plain validation key on `/login/index.php`.
2. App hashes it with SHA-256.
3. App stores the hash in cookie `validation`.
4. Protected pages include `login/validate.php`.
5. `validate.php` compares cookie value against lines in `validkeys.txt` (exact string match).
6. If match: access granted and cookie expiration is refreshed.
7. If no match: HTTP 403.

### Important detail

`validkeys.txt` must contain **hashes** (the same SHA-256 format), not plain text keys.

## 11. Setting Up Authentication

1. Generate hash by using login page:
   - open `http://localhost/zendure/login/index.php`
   - enter your key
   - copy shown hash
2. Add hash as a separate line in:
   - `[install_dir]/login/validkeys.txt`
3. Retry protected page, e.g.:
   - `http://localhost/zendure/main/charge_schedule_mobile.php`

## 12. Security Notes

- In production, set debug off in `validate.php`:
  - `define('LOGIN_VALIDATION_DEBUG', false);`
- Use HTTPS in production so cookie transport is protected.
- Restrict file permissions for:
  - `main/config/config.json`
  - `automate/config/config.jsonc`
  - `login/validkeys.txt`

## 14. Common Issues

- **403 Access Denied**
  - cookie missing/expired
  - hash not present in `validkeys.txt`
- **No schedule data**
  - wrong `scheduleApiUrl`
  - invalid JSON in schedule files
- **No condition merge**
  - `include_conditions` missing or false in `main/config/config.json`
- **Automation not acting**
  - `TEST_MODE` still true
  - incorrect `deviceIp` / `deviceSn` / P1 config
